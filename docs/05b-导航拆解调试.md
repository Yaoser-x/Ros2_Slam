# 导航拆解调试

本文档用于诊断导航链路异常时的分步排查。日常使用优先执行 `./bin/robot navigation ...`。

## 0. 底盘控制验证

仅启动 `stm32_bridge`，不启动雷达、AMCL、Nav2、RViz：

```bash
./bin/robot base-test --rotate-only
```

仅在 Gate B/C 条件满足、架空轮或低速有人看护时执行。期望现象：

- 车原地左转一小段，再原地右转一小段
- `/chassis/host_motion_command`、STATUS/ACK 和 wheel observation 持续更新
- 固件 STATUS 中 Host source、target 和 wheel facts 与测试阶段一致

原地转向稳定后，测试直线：

```bash
./bin/robot base-test --with-linear
```

### 角速度标定

量化命令角速度和实际角速度的差异：

```bash
./bin/robot base-test --calibrate-angular
```

自定义扫描档位：

```bash
BASE_TEST_ANGULAR_SERIES=0.5,1.0,1.5,2.0,2.5 ./bin/robot base-test --calibrate-angular
```

`Cmd log` 中输出 `CALIBRATION ...` 行，关键字段：

- `cmd_wz_deg_s` — 发给底盘的角速度命令
- `effective_wz_deg_s` — 根据 `/odom` 计算的实际平均角速度
- `response_ratio` — 实际角速度 / 命令角速度

标定结果可直接判断：

- 底盘从哪个角速度开始克服静摩擦
- 左转和右转是否不对称
- 导航参数中的 `min_speed_theta` 应设到什么量级

如果小角速度几乎不动、1.0~2.0 rad/s 才进入可用区、左右转不对称，调参策略：

- 抬高 `min_speed_theta`，避开无效小转向
- 放宽 `yaw_goal_tolerance`，减少终点附近反复小角修正
- 将 1.0~1.8 rad/s 作为主要工作区

方向反了应先修复底盘层线速度、角速度方向或里程计符号，而非修改 Nav2 参数。`status=NO_ODOM` 说明测试阶段未收到有效 `/odom`。

## 1. 里程计和 TF

下位机已接受 `/chassis/host_motion_command` 对应的 Host 候选后，验证 `/odom` 和 TF：

```bash
ros2 topic echo /odom --once
ros2 run tf2_ros tf2_echo odom base_link
```

期望：

- 车前进时 `odom.pose.pose.position.x` 增加
- 原地左转时 yaw 方向与实际一致
- `odom → base_link` 持续可查

## 2. 雷达和外参

确认雷达点云与车体方向一致：

```bash
./bin/robot sensor lidar
```

另一终端：

```bash
ros2 topic hz /scan
ros2 run tf2_ros tf2_echo base_link laser_frame
```

期望：

- `/scan` 频率稳定
- RViz 中车前方障碍物显示在 `base_link` 前方
- `Fixed Frame=base_link` 且只看 `LaserScan` 时，左侧障碍物显示在左侧

左右镜像处理顺序：

1. 检查事实源 `src/robot_config/config/components/lidar.yaml` 中的
   `inverted`；`src/robot_sensing/config/ydlidar_x2.yaml` 只是包内兼容默认
2. 测试 `--lidar-inverted` / `--no-lidar-inverted`
3. 测试 `--lidar-reversion` 或 `--lidar-yaw-*`
4. 错误手性下建出的旧地图直接废弃

## 3. 建图和保存

底盘、里程计、雷达都稳定后再建图：

```bash
./bin/robot mapping lidar --real-base
MAP_PADDING_METERS=1.5 ./bin/robot save-map my_map
```

## 4. AMCL 定位

标准导航流程异常时，单独拉起定位链：

```bash
./bin/robot navigation /home/robot/ros2_maps/my_map.yaml --real-base --localization-only
```

RViz 中使用 `2D Pose Estimate` 设置当前位置。期望激光点与地图墙面重合。

## 5. 全局规划

AMCL 对齐后再开 Nav2：

```bash
./bin/robot navigation --nav2-only
```

`--nav2-only` 启动前检查 `/map_server`、`/amcl` 是否 active，并等待 `/amcl_pose`。

RViz 中用 `2D Goal Pose` 点目标，先只看 `/plan` 是否生成。

## 6. 局部控制

`/plan` 有路线但车不按路线走时：

```bash
ros2 topic hz /cmd_vel/nav
ros2 topic hz /chassis/host_motion_command
ros2 topic echo /chassis/host_motion_command
ros2 topic echo /local_plan
```

判断 Nav2 是否持续给底盘发速度，以及局部轨迹是否合理。

## 7. Nav2 关键参数

参数事实源：`src/robot_config/config/components/nav2/base.yaml` 和 profile overlay；
运行时读取编译产物。`src/robot_bringup/config/nav2_params_robot.yaml` 仅是安装兼容文件。

当前 Humble 使用 `behavior_server`、`nav2_behaviors` 插件和
`nav2_amcl::DifferentialMotionModel`。恢复行为仍为旋转、后退、等待，数值策略不变。
启动包装器把既有 `nav2_bt_xml_file` 写入实际参数 `default_nav_to_pose_bt_xml`；
Humble 默认多目标树需要的 `ComputePathThroughPoses`、`RemovePassedGoals` 插件也必须加载，
否则同一 `bt_navigator` 的生命周期激活会失败。

公开导航入口为守卫的 `navigate_to_pose` Action。RViz 普通 `2D Goal Pose` 的
`goal_pose` 消息由守卫转入这个 Action，仍执行许可、取消和旧目标终止检查。
忙碌、许可过期或服务未就绪时明确拒绝，本轮目标不会在恢复后自动重放。
Nav2 后端的 Pose/ThroughPoses Action 和直接目标 topic 位于 `nav2/`；
当前不提供公开 ThroughPoses 守卫接口。

配置与原生 launch 替换回归：`tests/deployment/test_nav2_humble_contract.py`；
RViz 消息经过公开 Action 的 executor 回归：`navigation_pose` 场景。
这些主机检查不替代带实测 TF、地图和观测的 Nav2/车辆验收。

### 控制器参数（DWB Planner）

| 参数 | 当前值 | 说明 |
|------|--------|------|
| `controller_frequency` | 15.0 Hz | 局部控制频率 |
| `max_vel_x` | 0.26 m/s | 最大线速度 |
| `max_vel_theta` | 1.00 rad/s | 最大角速度 |
| `min_speed_theta` | 0.40 rad/s | 最小有效角速度，低于此值视为无效 |
| `yaw_goal_tolerance` | 0.35 rad | 航向目标容差 |

### 代价地图参数

| 参数 | 当前值 | 说明 |
|------|--------|------|
| `footprint` | `[[0.11, 0.075], [0.11, -0.075], [-0.11, -0.075], [-0.11, 0.075]]` | 车体外廓（22cm × 15cm） |
| `inflation_radius` | 0.25m | 障碍物膨胀半径 |
| `planner_frequency` | 5.0 Hz (全局) | 全局规划频率 |

### 行为树结构

默认导航 BT：`navigate_to_pose_recovery.xml`

```text
RecoveryNode(retries=6) "NavigateRecovery"
├── PipelineSequence "NavigateWithReplanning"
│   ├── RateController(1Hz)
│   │   └── RecoveryNode(retries=1) "ComputePathToPose"
│   │       ├── ComputePathToPose(planner_id=GridBased)
│   │       └── ClearEntireCostmap(global)
│   └── RecoveryNode(retries=1) "FollowPath"
│       ├── FollowPath(controller_id=FollowPath)
│       └── ClearEntireCostmap(local)
└── ReactiveFallback "NavigateRecoveryFallback"
    ├── GoalUpdated()
    └── RoundRobin "NavigateRecoveryActions"
        ├── ClearCostmaps(local + global)
        ├── Spin(1.57 rad)
        ├── Wait(4.0 s)
        └── BackUp(0.20 m, 0.05 m/s)
```

行为树节点含义：

| 节点 | 功能 |
|------|------|
| `ComputePathToPose` | 全局路径规划 |
| `FollowPath` | 局部路径跟踪 |
| `ClearEntireCostmap` | 清空代价地图 |
| `Spin` | 原地旋转（用于清除局部障碍） |
| `BackUp` | 低速倒车脱困 |
| `Wait` | 等待，让传感器数据更新 |
| `GoalUpdated` | 检测是否有新目标 |
| `RateController` | 控制子树执行频率 |

### 恢复行为流程

当路径跟踪失败时，行为树执行以下恢复序列（RoundRobin 轮询）：

1. 清空局部和全局代价地图
2. 原地旋转 90 度（1.57 rad）
3. 等待 4 秒
4. 低速倒车 0.20 m

每种恢复动作执行后重新尝试规划。6 次重试全部失败后放弃导航。

## 8. 面板导航

前面步骤都稳定后再做面板按钮或网页点选。面板本质上只需发布 `NavigateToPose` action 或 `/goal_pose`。

## 9. 重复导航验收

调 Nav2 前必须先完成
`verification/reports/calibration/v0.6.0-rc2-vehicle-dynamics.yaml`，实测最低稳定
直线/旋转速度、启动死区、制动距离和最大稳定加速度。数值为空时不得开始正式调参。

在固定地图上选取 10 个代表性目标，写入
`verification/configs/experiments/nav2-acceptance-v0.6.0-rc2.yaml`，每点重复 5 次。
数据必须来自独立验证集，每条记录成功、终点误差、恢复次数、碰撞、人工接管和
通信降级。

```bash
# 先检查定义和动态报告均已填写，再使用验证 runner 记录 50 次结果
python3 scripts/verify/verify_release.py
```

发布门要求至少 50 次、成功率不低于 90%、位置 p95 ≤ 0.20 m、角度 p95 ≤
0.35 rad、恢复总数 ≤ 10，且碰撞、人工接管和通信降级全部为零。任意目标重复次数
不足、地图 hash 或字段未填都会失败。
