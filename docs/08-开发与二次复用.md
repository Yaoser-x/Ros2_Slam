# 开发与二次复用

本文档面向需要修改或扩展工程的开发者。

## 1. 复用边界

工程的分层边界明确：

| 层级 | 入口 | 职责 |
|------|------|------|
| 运维层 | `bin/robot` | 用户意图 → 标准命令 |
| 编排层 | `src/robot_bringup/launch/system.launch.py` | 模式组合 → 节点组装 |
| 包级 | 各包的 `launch/` 目录 | 单包启动逻辑 |
| 参数 | `src/robot_config/config/` | 人工维护的唯一配置事实源 |
| 生成物 | `ROBOT_EFFECTIVE_*` | 本次运行编译出的参数，不反向编辑 |
| 第三方 | `deps/*.repos` + Git 忽略的 `vendor/` / `src/vendor/` | 依赖锁定与本地拉取 |

## 2. 新增能力的修改顺序

新增一类模式或功能时，按以下顺序修改：

1. 先更新职责、所有权、接口和验证顺序
2. 更新 `robot_config` schema/profile/component，由编译器生成运行参数
3. 在现有领域包中添加纯逻辑和 ROS 适配，仅在具有独立所有权时新增包
4. 必要时更新 `system.launch.py` 和 `bin/robot`
5. 更新架构、契约、验证和运维文档

不建议在外层新增平行的 shell 脚本入口。

## 3. 新增传感器

新增传感器通常需要处理：

- 设备驱动启动（launch 文件）
- 参数文件（`config/` 目录）
- 话题命名和 remapping
- 是否接入 `slam_toolbox` 或 Nav2
- RViz 配置更新

如果传感器参与建图或导航，应在 `system.launch.py` 中编排，而非独立入口。

## 4. 新增模式

工程当前支持 `mapping`、`navigation` 和 `base_only` 三种模式。新增模式时评估：

- 是否可作为 `system.launch.py` 的新 `mode` 值
- 是否仅是现有模式的参数组合

大多数情况下后者更合适。`base_only` 复用正式底盘控制和观测链，供独立运行与底盘验收。
`auto_mapping_drive=true` 会被 bringup 明确拒绝，
frontier explorer 仅保存在 `experiments/legacy`，不能当作正式能力。

## 5. Git 提交规范

本项目提交使用标准前缀首字母大写 + 中文标题 + 中文说明的格式。

### 标题格式

```text
Prefix: 中文提交标题
```

### 允许的前缀

| 前缀 | 用途 |
|------|------|
| `Feat:` | 新增功能 |
| `Fix:` | 修复问题 |
| `Refactor:` | 重构代码 |
| `Chore:` | 工程配置、依赖、脚本 |
| `Docs:` | 文档修改 |
| `Style:` | 代码格式调整 |
| `Test:` | 测试脚本或用例 |
| `Perf:` | 性能优化 |
| `Build:` | 构建系统修改 |
| `Ci:` | 持续集成 |
| `Revert:` | 回退提交 |

### 提交说明要求

说明必须使用中文，包含以下内容：

1. 本次修改了什么
2. 为什么修改
3. 是否影响树莓派部署
4. 是否影响雷达、底盘串口、TF、odom、Nav2 或建图链路
5. 是否需要同步修改下位机协议
6. 已执行哪些验证命令

### 提交示例

```text
Refactor: 重构 STM32 bridge 以适配 v3 会话协议

- 移除旧协议兼容逻辑
- 新增 v3 HELLO、session ACK 和 MCU sample timestamp
- 新增 65 字节 STATUS 帧解析
- 本次修改需要与下位机协议同步
- 已验证 colcon build 通过
```

### 禁止的提交标题

`update`、`fix`、`test`、`修改`、`临时提交` 等无意义标题。

## 6. 分支策略

| 分支 | 用途 |
|------|------|
| `main` | 主分支 |
| `ARM` | 树莓派 4B 上位机工作分支（当前活跃） |

```bash
git checkout -b ARM main
```

## 8. 新增 ROS2 包的模板

本项目所有包均使用 `ament_cmake` 构建（包括纯 Python 包），以下为 CMake 风格模板。

### 包结构（ament_cmake）

```text
src/my_package/
├── src/
│   └── my_node.cpp          # C++ 节点（或 scripts/my_node.py 纯 Python）
├── include/
│   └── my_package/
│       └── my_header.hpp
├── launch/
│   └── my_launch.py
├── config/
│   └── my_params.yaml
├── CMakeLists.txt
└── package.xml
```

### package.xml 要点（ament_cmake）

```xml
<?xml version="1.0"?>
<package format="3">
  <name>my_package</name>
  <version>0.1.0</version>
  <description>Package description</description>
  <maintainer email="dev@example.com">Author</maintainer>
  <license>Apache-2.0</license>

  <buildtool_depend>ament_cmake</buildtool_depend>

  <depend>rclcpp</depend>
  <depend>std_msgs</depend>

  <test_depend>ament_lint_auto</test_depend>
  <test_depend>ament_lint_common</test_depend>

  <export>
    <build_type>ament_cmake</build_type>
  </export>
</package>
```

### CMakeLists.txt 要点

```cmake
cmake_minimum_required(VERSION 3.5)
project(my_package)

if(NOT CMAKE_CXX_STANDARD)
  set(CMAKE_CXX_STANDARD 17)
endif()

find_package(ament_cmake REQUIRED)
find_package(rclcpp REQUIRED)
find_package(std_msgs REQUIRED)

add_executable(my_node src/my_node.cpp)
ament_target_dependencies(my_node rclcpp std_msgs)

install(TARGETS my_node DESTINATION lib/${PROJECT_NAME})
install(DIRECTORY launch config DESTINATION share/${PROJECT_NAME})

ament_package()
```

### 集成到 system.launch.py

1. 在 `system.launch.py` 中添加 `IncludeLaunchDescription` 或 `Node`
2. 通过 `DeclareLaunchArgument` 添加控制参数
3. 在 `_validate_and_compose()` 函数中添加条件逻辑

## 9. 参数设计建议

- 参数名保持稳定，避免频繁重命名
- 运行默认值写入 `robot_config` 事实源，launch 只提供显式的组合入口
- 未知字段、重复 YAML key、NaN/Inf 和跨参数不变量必须在编译时失败
- 用户入口（`bin/robot`）只传关键意图，不绕过配置编译器
- 兼容旧参数时保留过渡层，但设置明确的废弃时间
